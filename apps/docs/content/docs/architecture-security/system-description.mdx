Organizational AI Memory is a set of services that you deploy on your own
infrastructure: five services and a command-line client around four
infrastructure dependencies. Content comes in through connectors and uploads.
Every original byte is kept as immutable evidence, and people and AI agents
only ever see what they are allowed to see.

This page describes what runs, how the services talk to each other, and where
data and authority live. The lifecycle and authorization pages build on it.

## Core components

### Application layer

- **`apps/web`** — React product shell for the Assistant, Assets, governance,
  administration, and MCP connection setup. Knowledge search for agents is
  delivered over MCP, not through the web app.
- **`apps/api`** — Spring Boot REST server that handles business logic for
  browser and bearer clients, publishes the OpenAPI contract, and is the only
  service that runs database migrations.
- **`apps/worker`** — background service that polls connectors, leases
  ingestion jobs, parses and embeds content, and publishes the search and
  graph projections.
- **`apps/mcp`** — small stateless gateway that lets AI agents search
  Knowledge and fetch Assets over MCP. It has no database or domain-model
  access; it validates the caller's token and forwards the credential to the
  API.
- **`apps/cli`** — command-line client for connecting agents over MCP and for
  validating, publishing, and installing Skill packages.
- **`apps/docs`** — this documentation site. It is fully independent and never
  reads product databases.

The API and worker share the `core` domain model. Core depends on no
deployable application or provider integration.

### AI layer

Administrators configure model gateways per workload: Assistant chat, graph
extraction, keyword planning, and document embeddings. The shipped adapters
speak the OpenAI-compatible and Anthropic Messages protocols through Spring
AI. Model output is never trusted — extraction is validated before
publication, and retrieval evidence is authorized before it enters a prompt.

The default retrieval engine is GraphRAG with a server-owned plan that mixes
entity, relation, and chunk evidence. Clients cannot pick a strategy, widen
scope, or renumber citations. Reranking ships disabled and requires a named
adapter to enable.

### Data layer

- **PostgreSQL 18** — the source of truth: identity, source and Asset
  ledgers, immutable versions, sealed ACL generations, jobs, publication
  heads, audit trail, vectors, and graph contributions.
- **Object storage (MinIO)** — original file bytes and Skill packages,
  streamed only through authenticated application routes. There are no
  presigned URLs.

Full-text, vector, and graph records are rebuildable projections. If a
projection is lost, it is rebuilt from the ledger and the immutable bytes.

### Identity and authorization layer

- **Keycloak** — signs in browser users and issues tokens for agents. An
  external user becomes an actor only through an explicit OIDC issuer/subject
  binding; directory-managed provisioning (SCIM) runs on its own plane with
  credentials the product API rejects.
- **OpenFGA** — answers relationship questions for organizations, Knowledge
  Spaces, Knowledge Assets, and registry Assets, with a versioned model.
- **Source ACL evidence** — permissions captured from the source system form
  a separate, immutable ceiling on content reads that no admin grant can
  bypass.

[Authorization](/docs/architecture-security/authorization) covers the full
model.

## How the services talk to each other

- Browsers authenticate through the API's confidential OIDC flow against
  Keycloak and hold an HttpOnly session cookie — never a token.
- AI agents and the CLI present bearer tokens to the MCP gateway, which
  validates audience and scope, applies rate limits, and forwards the caller's
  credential to the API.
- Both paths converge on one canonical actor. The API derives identity,
  organization, and department server-side; token roles, email, and display
  attributes are never authorization inputs.
- Only the API and worker open database connections. The worker validates the
  schema and never runs migrations.

## Component replacements

- Model providers, object storage, connectors, observability, and sidecar
  decoding are ports — adapters can be swapped without touching the domain.
- OpenSearch and Neo4j adapters exist for the graph and search projections but
  are not part of the default deployment.
- The PostgreSQL ledger is not replaceable. It is the evidence authority that
  every projection rebuilds from, and exact Asset releases are immutable by
  database constraint.
- Replacing an adapter never moves authorization into it. Adapters return
  candidates; the application always performs the final recheck.
