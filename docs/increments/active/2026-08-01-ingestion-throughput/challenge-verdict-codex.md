# Ingestion Throughput Architecture Challenge Verdict

**Review basis:** branch `increment/ingestion-throughput`, HEAD `488a122cf4df7d66c67092235fbb65699b5e0f36`, reviewed read-only on 2026-08-01. I independently read the required repository guidance, ingestion spec, decision filenames, current implementation, and the Onyx comparison checkout.

## Executive verdict

| Decision | Verdict | Bottom line |
|---|---|---|
| 1. Replace per-row staging writes with `batchUpdate` | **APPROVE-WITH-MUST-FIX** | The ordinary content/lexical/vector loops have whole-stage failure semantics and no observed per-row result dependency, but the proposal incorrectly treats graph and cache loops as mechanically equivalent. Graph writes need dependency-phased batches; retrieval cache must retain its returned-key and ordinal contract; all batches must be bounded. |
| 2. Replace one-job ticks with drain-until-empty | **REJECT** | In this application an unbounded drain executes inside Spring's shared default scheduling executor. It can starve the other ingestion queue and every maintenance scheduler indefinitely. Leases protect claims, not scheduler fairness or shutdown responsiveness. |

## Decision 1 — JDBC batching

### Findings

1. **Content, lexical, and vector callers do not observe per-statement attribution.** Each loop invokes `jdbc.update` and ignores its count (`PostgresContentStore.java:56-58`, `PostgresLexicalIndex.java:57-59`, `PostgresVectorIndex.java:57-59`). `PostgresProjectionSupport.stage` executes copy-forward and all mutations in one `TransactionTemplate` callback (`PostgresProjectionSupport.java:52-80`). Any runtime failure exits the preparation, and the lifecycle aborts/discards the whole batch; its only persisted reason is the exception class name, not a row index or update-count vector (`ProjectionBatchLifecycle.java:37-50`, `ProjectionBatchLifecycle.java:53-68`). Therefore callers already observe whole-stage success/failure, not partial progress.

2. **The graph store is not one homogeneous loop whose exact statement order can be preserved by a single batch call.** Replacement currently performs revision deletion, then entity upserts, then relation upserts, then orphan cleanup (`PostgresGraphStore.java:143-147`). Every entity executes two different SQL statements in sequence—entity row then contribution row (`PostgresGraphStore.java:510-559`); every relation likewise executes relation row then contribution row (`PostgresGraphStore.java:562-614`). `NamedParameterJdbcTemplate.batchUpdate` batches one SQL shape, so the design's promise to preserve the exact alternating statement order is not implementable literally. The safe structure is dependency-phased batches: delete revision; entity base rows; entity contributions; relation base rows; relation contributions; orphan removal. That is a deliberate ordering change requiring PostgreSQL integration proof.

3. **The cache store is misclassified as a generation-staging store.** Its model-cache `put` is a single upsert, not a per-row staging loop (`PostgresGraphRagCacheStore.java:67-117`). Retrieval-cache `put` is transactional, first obtains the cache-entry UUID through `INSERT ... RETURNING id`, then deletes old evidence, then inserts ordered evidence rows (`PostgresGraphRagCacheStore.java:192-247`, `PostgresGraphRagCacheStore.java:261-325`). Reads restore evidence using `ORDER BY ordinal` (`PostgresGraphRagCacheStore.java:164-182`). Only the evidence inserts are batchable; the returned-key dependency, delete-before-insert order, and ordinals are contract-bearing.

4. **Batching need not change the publication transaction boundary.** Today copy-forward and one store's mutations share one staging transaction (`PostgresProjectionSupport.java:52-80`), while each preparation commits before its durable receipt and final publish (`ProjectionBatchLifecycle.java:15-18`, `ProjectionBatchLifecycle.java:38-46`). Final publication uses a separate transaction, locks the namespace, verifies all durable receipts, performs generation CAS, then rotates the head (`PostgresProjectionPublicationStore.java:142-148`, `PostgresProjectionPublicationStore.java:240-299`). Keeping batch calls inside the existing `support.stage` callback preserves those boundaries. It may reduce round-trip duration, but it also acquires many row locks in bursts; this is a deadlock/memory exposure if implemented as an unbounded batch.

5. **Unbounded batches would contradict an existing architecture decision.** The worker allows up to 500 chunks and graph extraction allows up to 40 entities plus 60 relations per chunk (`apps/worker/src/main/resources/application.yml:105-110`), so one document can produce tens of thousands of graph parameters. Decision 0011 explicitly requires record/payload-bounded batches (`docs/decisions/0011-postgresql-multimodel-graph-projection.md:42-45`). Batching must use bounded sub-batches while retaining stable input order inside each phase.

### Must-fix before implementation

- Rewrite the scope store-by-store: ordinary staging loops (content/lexical/vector), dependency-phased graph writes, and retrieval-evidence cache writes. Do not claim model-cache batching or call retrieval cache generation staging.
- Keep every sub-batch inside the existing `support.stage`/cache transaction. Preserve delete/copy-forward/base/contribution/orphan dependency order and retrieval `RETURNING id` plus ordinal behavior.
- Introduce an explicit bounded batch size; do not allocate one parameter array for the maximum document. Preserve source order within each sub-batch.
- Preserve current exception translation as one failed preparation. Do not invent per-row retry or partial-success semantics from `BatchUpdateException`; no caller currently consumes them.
- Add real PostgreSQL integration tests for: a middle-row constraint violation rolls back the whole store stage and creates no preparation receipt; copy-forward plus failed mutation leaves no publishable partial generation; graph FK/dependency ordering; retrieval evidence readback order; and concurrent publication/deadlock behavior at batch boundaries.

## Decision 2 — Drain-until-empty schedulers

### Findings

1. **A tick is currently exactly one job.** Source scheduling invokes one `processNext` after a two-second fixed delay (`SourceIngestionScheduler.java:21-23`); graph scheduling invokes one after a three-second delay (`GraphIndexingScheduler.java:21-23`). Both processors perform one `claimNext(...).ifPresent(...)` and return `void` (`SourceIngestionProcessor.java:126-129`, `GraphIndexingProcessor.java:119-122`). Under Spring's documented `fixedDelay` contract, the delay is measured from completion of one invocation to the start of the next. A drain implementation therefore also needs a processor contract change (for example, `PROCESSED` versus `EMPTY/DEFERRED`); a wrapper around today's `void processNext()` cannot know when to stop without an additional claim.

2. **The proposal overlooks the actual scheduler topology.** The app only enables scheduling (`OrgMemoryWorkerApplication.java:24`). A repository-wide scan finds no `TaskScheduler`, `SchedulingConfigurer`, `ScheduledTaskRegistrar`, `ThreadPoolTaskScheduler`, or `spring.task.scheduling.*` configuration. Spring's current `@EnableScheduling` contract falls back to a local single-threaded scheduler when none is supplied. That same application also schedules connector crawl, two authorization convergence jobs, and skill-package cleanup (`ConnectorCrawlScheduler.java:25`, `AssetAuthorizationConvergenceScheduler.java:31`, `KnowledgeAuthorizationConvergenceScheduler.java:36`, `SkillPackageSupersessionCleanupScheduler.java:24`). An unbounded source drain can therefore prevent graph indexing—the queue source ingestion feeds—from ever running, and either drain can block all maintenance jobs. `Thread.yield()` or an interrupt check between jobs does not return the sole executor thread to its scheduled-task queue; returning does, but then the algorithm is a bounded burst rather than drain-until-empty.

3. **Leases make one claim multi-replica safe, not an unbounded drain or exactly-once execution safe.** Both repositories select one pending or expired-processing row with `FOR UPDATE SKIP LOCKED LIMIT 1` (`SourceIngestionJobRepository.java:12-24`, `GraphIndexJobRepository.java:18-34`), and claim operations are transactional (`SourceIngestionCoordinator.java:32-42`, `GraphIndexingCoordinator.java:59-91`). Two replicas cannot transactionally acquire the same current row at the same instant. However, expired processing rows are intentionally reclaimable. Long-running work can therefore execute more than once across a lease expiry; correctness relies on ownership revalidation and idempotent/publication boundaries, not exactly-once execution.

4. **Lease renewal is asymmetric and does not justify the proposal's claim.** Source ingestion renews only at stage transitions (`SourceIngestionProcessor.java:186-190`, `SourceIngestionProcessor.java:222-257`); parse/processing and embedding calls run between those renewals (`SourceIngestionProcessor.java:193-200`, `SourceIngestionProcessor.java:248-252`). Its ownership check validates worker identity but not lease expiry (`SourceIngestionCoordinator.java:136-141`). Graph extraction is stronger: it refreshes after concurrency windows and during waits at one-third of the lease interval (`GraphIndexingProcessor.java:453-480`, `GraphIndexingProcessor.java:485-513`), and its coordinator rejects expired leases (`GraphIndexingCoordinator.java:268-277`). Neither mechanism supplies fairness between scheduler callbacks, and neither converts lease recovery into exactly-once processing.

5. **Shutdown responsiveness is not preserved by the described loop.** Production config sets only the global shutdown-phase timeout (`apps/worker/src/main/resources/application-prod.yml:1-3`), with no scheduling-executor wait/termination policy. Under Spring's default scheduling shutdown behavior, context close cancels scheduled work best-effort; the graph processor explicitly restores interrupt status and leaves the lease to expire (`GraphIndexingProcessor.java:222-226`) and cancels extraction futures on interruption (`GraphIndexingProcessor.java:471-480`). Source processing has no explicit interrupt branch; it routes operational exceptions through generic retry handling (`SourceIngestionProcessor.java:294-310`). An unbounded outer loop must at minimum stop before the next claim when interrupted or closing, but that still does not solve shared-pool starvation while the current job is running.

6. **Onyx is evidence against a shared-scheduler drain.** Onyx periodically dispatches indexing discovery every 15 seconds (`D:/OrgMemory/tmp/onyx/backend/onyx/background/celery/tasks/beat_schedule.py:71-78`), but its fetcher stores each document batch and sends a broker task to the dedicated `DOCPROCESSING` queue (`D:/OrgMemory/tmp/onyx/backend/onyx/background/indexing/run_docfetching.py:777-810`). Each broker task processes one document batch (`D:/OrgMemory/tmp/onyx/backend/onyx/background/celery/tasks/docprocessing/tasks.py:1487-1502`), consumed continuously by a dedicated thread worker with configured concurrency and prefetch 1 (`D:/OrgMemory/tmp/onyx/backend/onyx/background/celery/configs/docprocessing.py:27-29`); late acknowledgements are enabled (`D:/OrgMemory/tmp/onyx/backend/onyx/background/celery/configs/base.py:132`). Onyx is a hybrid—periodic discovery plus continuously consuming isolated workers—not one job per discovery tick and not an unbounded loop monopolizing a shared scheduler.

### Required redesign

- Reject `drain-until-empty` inside the current shared `@Scheduled` callback.
- The smallest in-scope alternative is a **bounded burst**: stop on `EMPTY/DEFERRED`, `maxJobsPerInvocation`, wall-clock budget, interrupt, or application stop; then return so other scheduled work can run. Configure separate budgets for source and graph queues.
- If true continuous draining is required, use dedicated executors/consumers per queue with explicit lifecycle and concurrency. That is the architecture Onyx's isolation supports, but it conflicts with this design's stated non-goal of no new scheduling infrastructure (`design.md:40-47`) and therefore belongs in a revised design or separate increment.
- Add tests for empty/deferred termination, burst cap, interrupt-before-next-claim, source-vs-graph fairness under simultaneous backlog, maintenance-task opportunity, two-replica claim behavior, expired-lease duplicate execution, and shutdown leaving the current job retryable without claiming another.

## Strongest counterargument

The strongest defense is that batching remains inside existing transactions and `SKIP LOCKED` leases make repeated claims safe, so both changes appear to be mechanical throughput optimizations. That defense is persuasive for bounded, dependency-aware JDBC batching. It fails for scheduling: database claim exclusivity says nothing about executor fairness, and the repository has one default scheduling thread shared by all queues and maintenance callbacks. A cooperative stop check prevents one additional claim after shutdown; it cannot let another scheduled callback run while the drain method refuses to return.
