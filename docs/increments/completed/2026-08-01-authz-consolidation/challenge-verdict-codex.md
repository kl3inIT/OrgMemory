# Architecture Challenge Verdict — Authorization Consolidation

## Decision 1 — Shared OpenFGA batch-recheck collaborator

**VERDICT: APPROVE-WITH-MUST-FIX**

The three copies share mechanics—deduplicate `knowledge_asset` resources, call `BatchCheck`, fail closed on unresolved/incomplete results—but they are **not observably equivalent**, so a collaborator parameterized only by a deny-reason string is unsafe.

| Surface | Empty handling | Batch/model/incomplete handling | Explicit per-resource deny | Observable surface |
|---|---|---|---|---|
| Canonical citation evidence | Rejects an empty chunk request with `IllegalArgumentException` (`core/src/main/java/com/orgmemory/core/knowledge/retrieval/CanonicalEvidenceAuthorizationService.java:50`). | Unresolved result, outer model mismatch, and count mismatch are collapsed to `checked.reasonCode()` (`core/src/main/java/com/orgmemory/core/knowledge/retrieval/CanonicalEvidenceAuthorizationService.java:164`). | Missing, denied, and per-decision model mismatch are all collapsed to `CITATION_OPENFGA_RECHECK_DENIED` (`core/src/main/java/com/orgmemory/core/knowledge/retrieval/CanonicalEvidenceAuthorizationService.java:174`). | The citation service converts that authorization exception to the same not-found response used for missing content (`core/src/main/java/com/orgmemory/core/knowledge/retrieval/CitationContentService.java:59`), matching the generic-404 contract (`docs/specs/domains/secure-retrieval.md:25`). |
| Canonical hybrid search | Returns an allowed empty result when no authorized assets or no ranked evidence exist (`core/src/main/java/com/orgmemory/core/knowledge/retrieval/CanonicalHybridKnowledgeSearch.java:90`, `core/src/main/java/com/orgmemory/core/knowledge/retrieval/CanonicalHybridKnowledgeSearch.java:131`). | Unresolved/count mismatch propagates the provider reason; outer and per-decision model mismatch use the distinct `AUTHORIZATION_MODEL_MISMATCH`; a missing decision uses `OPENFGA_BATCH_INCOMPLETE` (`core/src/main/java/com/orgmemory/core/knowledge/retrieval/CanonicalHybridKnowledgeSearch.java:150`, `core/src/main/java/com/orgmemory/core/knowledge/retrieval/CanonicalHybridKnowledgeSearch.java:160`, `core/src/main/java/com/orgmemory/core/knowledge/retrieval/CanonicalHybridKnowledgeSearch.java:169`). | A resolved deny is **filtered out**, not fatal; only allowed asset IDs survive (`core/src/main/java/com/orgmemory/core/knowledge/retrieval/CanonicalHybridKnowledgeSearch.java:187`). A later canonical miss is audited and omitted (`core/src/main/java/com/orgmemory/core/knowledge/retrieval/CanonicalHybridKnowledgeSearch.java:212`). | Partial authorized search results remain usable. |
| GraphRAG final closure | Returns an allowed empty result for no eligible or no citable grounding (`core/src/main/java/com/orgmemory/core/knowledge/retrieval/GraphRagKnowledgeRetrievalService.java:278`, `core/src/main/java/com/orgmemory/core/knowledge/retrieval/GraphRagKnowledgeRetrievalService.java:301`). | Unresolved result, outer model mismatch, and count mismatch are collapsed to `checked.reasonCode()` (`core/src/main/java/com/orgmemory/core/knowledge/retrieval/GraphRagKnowledgeRetrievalService.java:774`). | Any missing, denied, or per-decision model mismatch fails the **whole request** as `FINAL_OPENFGA_RECHECK_DENIED` (`core/src/main/java/com/orgmemory/core/knowledge/retrieval/GraphRagKnowledgeRetrievalService.java:784`). | Atomic closure is intentional: one failed snapshot fails the request and the complete selected closure must be BatchChecked and canonically reread (`docs/specs/domains/secure-graph-rag.md:122`, `docs/specs/domains/secure-graph-rag.md:127`). |

Interrupt behavior is common only because the OpenFGA adapter restores the thread interrupt flag and returns `OPENFGA_INTERRUPTED` (`integrations/authorization-openfga/src/main/java/com/orgmemory/integrations/authorization/openfga/OpenFgaRelationshipAuthorizationSetAdapter.java:117`). The shared collaborator must propagate that indeterminate reason without clearing the flag. The current interruption test exercises `listAuthorizedResources`, not `batchCheck` (`integrations/authorization-openfga/src/test/java/com/orgmemory/integrations/authorization/openfga/OpenFgaRelationshipAuthorizationSetAdapterTests.java:153`), so batch-path characterization is required.

The policy distinction has a product reason, not just accidental drift. Search can reduce a candidate set to currently visible evidence, while a citation open represents one requested object and GraphRAG declares the selected evidence closure an atomic authorization snapshot (`docs/specs/domains/secure-retrieval.md:12`, `docs/specs/domains/secure-graph-rag.md:127`). This also preserves ADR 0003's rule that OpenFGA outages/model mismatch fail closed and Java may deny more but must not create a second allow policy (`docs/decisions/0003-postgresql-ledger-openfga-authorization.md:22`, `docs/decisions/0003-postgresql-ledger-openfga-authorization.md:28`).

A safe collaborator therefore needs an explicit, typed result policy such as `FILTER_DENIED` versus `REQUIRE_ALL_ALLOWED`, not a boolean or deny-code parameter. Callers must retain their surface-specific mapping to search-unavailable, citation-not-visible/404, or filtered evidence. This keeps future divergence explicit: Graph closure remains atomic, citation visibility remains non-enumerating, and hybrid search remains reducible.

## Decision 2 — Publish `canDecide` and `canManage`

**VERDICT: REJECT**

The direction—remove browser-authored authorization arithmetic and publish server-computed display affordances—is correct, but the proposed two booleans do not represent current server policy.

Core already publishes actor-specific action permissions through `AssetGovernanceActions`, explicitly documented as UI affordances that never replace mutation authorization (`core/src/main/java/com/orgmemory/core/assetregistry/AssetGovernanceActions.java:3`). `AssetRegistryService` computes `canEdit`, `canSubmitReview`, `canReview`, `canPublish`, `canPublishSkill`, and `canWithdraw` from live authorization checks (`core/src/main/java/com/orgmemory/core/assetregistry/AssetRegistryService.java:209`), and mutation commands recheck `CAN_REVIEW` or `CAN_SUBMIT_REVIEW` (`core/src/main/java/com/orgmemory/core/assetregistry/AssetRegistryService.java:307`). It does **not** currently compute the proposed verdicts.

A single per-review `canDecide` is semantically false. Core forbids a revision author only from `APPROVE`; it does not forbid that author from `REQUEST_CHANGES` or `REJECT`, while `CANCEL` has a separate requester rule (`core/src/main/java/com/orgmemory/core/assetregistry/AssetRegistryCoordinator.java:591`, `core/src/main/java/com/orgmemory/core/assetregistry/AssetRegistryCoordinator.java:595`). The review entity independently requires `IN_REVIEW` for every decision (`core/src/main/java/com/orgmemory/core/assetregistry/AssetReviewCase.java:56`). The browser's local boolean instead excludes the author from every decision (`apps/web/src/features/assets/governance-policy.ts:31`) and uses that one boolean to hide both Approve and Request Changes (`apps/web/src/features/assets/components/governance-workspace-page.tsx:303`, `apps/web/src/features/assets/components/governance-workspace-page.tsx:352`). Publishing that boolean would move an existing client/server disagreement into the API rather than eliminate it.

`canManage` is also undefined by current Core policy. The browser currently treats admin or any direct non-viewer user assignment as management authority (`apps/web/src/features/assets/components/asset-detail-page.tsx:143`), but the OpenFGA model allows group membership and defines distinct action permissions with Space gates; it has `can_manage_roles`, not a general Asset `can_manage` permission (`integrations/authorization-openfga/src/main/openfga/model.fga:72`, `integrations/authorization-openfga/src/main/openfga/model.fga:85`). A reviewer, editor, publisher, steward, owner, and org admin intentionally receive different capabilities (`integrations/authorization-openfga/src/main/openfga/model.fga:86`). Therefore `canManage` must first be given one precise product meaning—such as “may open the governance workspace”—and be derived from the same Core action verdicts, not role labels or a new API-layer policy.

The `grantOptions()` precedent supports server publication only when one Core rule both validates commands and feeds the UI. The same `GRANTABLE_SUBJECTS` map is documented as the browser catalog (`core/src/main/java/com/orgmemory/core/knowledge/space/KnowledgeSpaceAdministrationService.java:52`), used to validate authored tuples (`core/src/main/java/com/orgmemory/core/knowledge/space/KnowledgeSpaceAdministrationService.java:258`, `core/src/main/java/com/orgmemory/core/knowledge/space/KnowledgeSpaceAdministrationService.java:400`), and returned by `grantOptions()` (`core/src/main/java/com/orgmemory/core/knowledge/space/KnowledgeSpaceAdministrationService.java:274`). The asset replacement should follow that pattern inside Core; the API controller should only serialize it.

The minimum truthful replacement is action-specific review affordances—at least `canApprove`, `canRequestChanges`, `canReject`, and `canCancel`—computed by the same Core predicate used by `decide`, plus either the existing asset action bundle or a precisely named `canOpenGovernance` derived from it. Mutation authorization must remain authoritative (`core/src/main/java/com/orgmemory/core/assetregistry/AssetGovernanceActions.java:6`).

## Contract Impact

Adding response fields is wire-additive, but rollout is not automatically risk-free. The generated web client currently represents `AssetView`, `Review`, and `AssetGovernanceActions` properties as optional (`apps/web/src/lib/hey-api/types.gen.ts:49`, `apps/web/src/lib/hey-api/types.gen.ts:116`, `apps/web/src/lib/hey-api/types.gen.ts:1155`), so a new browser must treat absent flags as false and the server should deploy first. Adding components to Java records is internally source-breaking at constructor sites, including the central `AssetView` construction and review mapping (`core/src/main/java/com/orgmemory/core/assetregistry/AssetRegistryCoordinator.java:910`, `core/src/main/java/com/orgmemory/core/assetregistry/AssetRegistryCoordinator.java:958`).

The repository MCP path is separate: it consumes `/api/asset-delivery/...` into its own `AssetRelease` DTO, not the governance `AssetView` endpoint (`apps/mcp/src/main/java/com/orgmemory/mcp/AssetDeliveryApiClient.java:54`, `apps/mcp/src/main/java/com/orgmemory/mcp/AssetDeliveryApiClient.java:197`). The scoped CLI search found no `/api/assets`, `/api/asset-delivery`, or `governance-actions` consumer. External strict JSON consumers are not inventoried, so compatibility outside this repository is unproven.

## Comparable-System Evidence — Onyx

Onyx supports the server-owned direction, not the proposed boolean shape. Before chat session creation it checks persona access on the server (`D:/OrgMemory/tmp/onyx/backend/onyx/chat/chat_utils.py:147`); its persona check applies database access filters (`D:/OrgMemory/tmp/onyx/backend/onyx/db/persona.py:1858`). User-supplied document-set names are checked server-side and unauthorized names are rejected (`D:/OrgMemory/tmp/onyx/backend/onyx/context/search/pipeline.py:56`), then the user's ACL and document-set/persona filters are placed into `IndexFilters` (`D:/OrgMemory/tmp/onyx/backend/onyx/context/search/pipeline.py:105`) and applied by the search query (`D:/OrgMemory/tmp/onyx/backend/onyx/document_index/opensearch/search.py:218`).

For UI affordances, Onyx computes `user_permission` on the server from direct ownership, owner groups, user/group shares, admin status, and public sharing (`D:/OrgMemory/tmp/onyx/backend/onyx/db/persona.py:793`, `D:/OrgMemory/tmp/onyx/backend/onyx/db/persona_sharing.py:50`). The web consumes that server verdict, with a compatibility fallback for older payloads (`D:/OrgMemory/tmp/onyx/web/src/lib/agents/utils.ts:10`, `D:/OrgMemory/tmp/onyx/web/src/lib/agents/utils.ts:27`). This is evidence for server-computed affordances plus server-side enforcement. It is not evidence that OrgMemory's three post-ranking OpenFGA rechecks are equivalent: Onyx applies index query filters and exposes an explicit `bypass_acl` path for system callers (`D:/OrgMemory/tmp/onyx/backend/onyx/context/search/pipeline.py:45`), whereas OrgMemory's graph contract requires a complete selected-closure recheck (`docs/specs/domains/secure-graph-rag.md:127`).

## Must-Fix List

1. Replace “deny-reason parameter” with an explicit typed policy/result model that distinguishes filter-denied search from require-all citation/Graph closure (`core/src/main/java/com/orgmemory/core/knowledge/retrieval/CanonicalHybridKnowledgeSearch.java:187`, `core/src/main/java/com/orgmemory/core/knowledge/retrieval/GraphRagKnowledgeRetrievalService.java:784`).
2. Preserve each surface's reason and exception mapping, including `AUTHORIZATION_MODEL_MISMATCH`, `OPENFGA_BATCH_INCOMPLETE`, provider indeterminate reasons, citation generic 404, and Graph's final-recheck reason (`core/src/main/java/com/orgmemory/core/knowledge/retrieval/CanonicalHybridKnowledgeSearch.java:160`, `core/src/main/java/com/orgmemory/core/knowledge/retrieval/CitationContentService.java:66`, `core/src/main/java/com/orgmemory/core/knowledge/retrieval/GraphRagKnowledgeRetrievalService.java:790`).
3. Characterize before swapping: empty inputs/upstream empties, duplicate resources, mixed allow/deny, missing decisions, outer and per-decision model mismatch, timeout/unavailable/interrupted results, preserved interrupt flag, audit reason, exception type, and partial-versus-atomic output. Existing tests pin citation denial and some hybrid failures but do not cover this full matrix (`core/src/test/java/com/orgmemory/core/knowledge/retrieval/CanonicalEvidenceAuthorizationServiceTests.java:88`, `core/src/test/java/com/orgmemory/core/knowledge/retrieval/CanonicalHybridKnowledgeSearchTests.java:120`, `core/src/test/java/com/orgmemory/core/knowledge/retrieval/GraphRagKnowledgeRetrievalServiceTests.java:334`).
4. Reject a single `canDecide`; publish action-specific per-review affordances from the exact Core mutation predicate, or intentionally change and document the product rule before changing the contract (`core/src/main/java/com/orgmemory/core/assetregistry/AssetRegistryCoordinator.java:591`, `apps/web/src/features/assets/components/governance-workspace-page.tsx:352`).
5. Define `canManage` precisely or replace it with `canOpenGovernance`/the existing action bundle; compute it in Core from live permissions, never from assignments or role labels (`core/src/main/java/com/orgmemory/core/assetregistry/AssetRegistryService.java:209`, `integrations/authorization-openfga/src/main/openfga/model.fga:85`).
6. Keep every mutation's live authorization and workflow validation after publishing UI flags, and test absent-field behavior for mixed-version rollout (`core/src/main/java/com/orgmemory/core/assetregistry/AssetGovernanceActions.java:6`, `apps/web/src/lib/hey-api/types.gen.ts:1155`).

## Strongest Counterargument

The strongest argument against Decision 1—even after these fixes—is that the duplication is safer than a generic abstraction because it keeps three materially different product failure policies visible at their call sites. A shared helper with booleans or callbacks would centralize syntax while hiding the exact distinction that prevents partial Graph/citation disclosure and unnecessary whole-search failure (`docs/specs/domains/secure-graph-rag.md:124`, `core/src/main/java/com/orgmemory/core/knowledge/retrieval/CanonicalHybridKnowledgeSearch.java:187`). I would change the Decision 1 verdict to **REJECT** if the implementation cannot make the policy mode mandatory, typed, exhaustive, and characterization-tested.
